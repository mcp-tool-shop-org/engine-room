ローカルAIエンジン用の、**レシピに基づいたプロビジョナー。** 検証済みの測定された「エンジンレシピ」のカタログを参照し、その中から1つを選択して、独自のGPU環境に展開します。**プロビジョン → 起動 → 測定** を実行し、リアルなパフォーマンス基準と比較しながら、再現性があり、必要に応じて実行できます。

## なぜか？

ローカルAIエンジンは非常に多様であり、それぞれ異なる方法で展開されます。あるものはソースコードからのCUDAビルド、次のものはコンテナ、その次はポータブルなバンドル、そしてファイルを作成して終了する量子化ツールです。どのエンジンを使用するかを決定することは1つの問題（ナレッジベースで解決できます）。実際に**正しく、再現性があり、動作することを確認しながら展開する**ことは別の問題です。
`engine-room`は後者の問題を解決します。

## アーキテクチャ - 2つの成果物、1つのインターフェース

`engine-room`は、意図的に分割されたものの**アクション**部分です。

- **ナレッジ** - 検証され、ソースが明確で、抽象的な*レシピ*（何をビルドするか、固定されたツールチェーン、測定されたベースラインターゲット、宣言されたロールバック手順）。アップストリームエンジンが変更されると、これも変更されます。ナレッジベースに保存されます。
- **アクション** - このリポジトリ：ライブ環境に対してレシピを解決し、それを具現化し、起動/測定を行い、安全にロールバックします。*環境*が変更されると、これも変更されます。

## レシピレイヤーの取得

`engine-room`は**アクション**部分であり、レシピ自体は含まれません。**ナレッジ**部分は、別途提供される検証済みの成果物です。それは**tensor-engine-knowledge**レシピデータベース（`engines.db`）であり、これを`er`に指定します。このリポジトリだけをクローンしても、カタログではなく実行エンジンしか得られません。

- **レシピデータベースなしで環境を検出:** `er rig`はライブハードウェアのみを読み取ります（`nvidia-smi` + 環境変数）、そのためすぐに使用できます。
- **その他のすべての操作のために、レシピデータベースを指定:** (`list` / `show` / `preflight` / `provision`) 2つの方法があります。
- `ER_RECIPES_DB`をデータベースのパスに設定するか、
- 任意のコマンドで`--db <path>`を渡します。
- いずれも設定されていない場合、`er`はリポジトリに対して`../../readouts/tensor-engine-knowledge/engines.db`を探します。データベースが見つからない場合は、明確なエラーが表示されます（「レシピデータベースが見つかりません：… $ER_RECIPES_DBを設定するか、--dbを渡してください」）、スタックトレースは表示されません。

レシピレイヤーは信頼できるナレッジ入力です（[セキュリティ/脅威モデル](#security--threat-model)を参照）。`engines.db`をtensor-engine-knowledgeディストリビューションから取得します。`engine-room`はこれを**読み取り専用**で読み込み、書き込みは行いません。

レシピは**ポリモーフィック**であり、それぞれ異なる形状を持つ4つの種類があります。

| 種類 | その機能 | 測定方法 |
|------|--------------|-------------|
| `launchable-server` | ポートで長期間実行されるサーバーを起動します | スループット（トークン/秒、反復/秒） |
| `batch-producer` | 実行し、成果物を書き出し、終了します | 出力品質 + 経過時間 |
| `modifier` | 別のレシピを高速化するドロップインオーバーレイ | 測定されたデルタ値 |
| `router-fleet` | 他のレシピにルーティングするフロントエンド | アップストリームごとの健全性 |

## 設計により、再現性と検証が可能です

- **固定化されたベンダー提供の成果物**（キュレーションされたインデックスに対するハッシュだけでは不十分です。インデックスからチャンネルが削除された場合、ピンはコンテンツアドレス指定されたコピーである必要があります）。
- **測定されたベースライン**はモデルにキー付けされ、互換性バンドを持ちます。そのため、通常のドライバーアップデートによって無効になることはありません。
- **パフォーマンスに関する主張を行う前に、正当性のゲートが実行されます。** これは出力形式ごとにプラグイン可能です。
- **すべての不可逆的なステップには、正直なロールバック後の状態を持つ名前付きの元に戻す操作があります。** マシン全体に影響を与えるものは、明示的なユーザー承認が必要です。

## ステータス

実行エンジンは実装されています。`er` CLIはレシピレイヤーを読み取り、ライブ環境に対してレシピを解決します（`rig` / `list` / `show` / `preflight`。これらはすべて副作用のない操作です）。そして、プロビジョナーが調整ループを実行します。**デフォルトではドライランで実行され、`--execute`パスを指定すると、固定化された成果物を具現化し、ローカルサーバーを起動し、レシピのベースラインに対して測定を行います（`provision` / `teardown` / `status`）。[executor/README.md](executor/README.md)を参照してください。

再現性は現在、完全に実現されているわけではありません。ピンはインデックスに対して解決され、固定されていない成果物も受け入れられます。**ゴール1**は、それらをコンテンツアドレス指定されたストアにベンダー提供することで、`reproducible`を*獲得する*ことです。

オペレーターUIは、自己完結型のプロトタイプとして提供されます（モックデータ+タイマーでシミュレートされた副作用、実際のJSON/WS APIに忠実です）。

- [`app/`] - コントロールパネル：レシピを参照して実行し、ライブテレメトリ、ANDONハルト、およびロールバックを行います。これは[`design/ui-control-panel.claude-design-brief.md`](design/ui-control-panel.claude-design-brief.md)（完全なイベントハンドラーマップとユーザビリティ要件）に基づいて設計されています。

## セキュリティ / 脅威モデル

**レシピレイヤー** (`tensor-engine-knowledge/engines.db`) は、信頼できるナレッジ入力です。検証され、ソースが明確なレシピであり、何をビルドし、どのターゲットを達成するかを示します。`engine-room`はこれを真実の唯一の情報源として扱います。

`er provision --execute` は、環境に影響を与える唯一のコマンドです。これは**明示的な `--execute` と `--model` の後にのみ実行されます**。他のすべてのコマンドと、`--execute`なしの`provision`は、読み取り専用/ドライランです。実行する場合、次の処理が行われます。

- **レシピの固定化された成果物をダウンロードし、ピンにshaが含まれている場合はsha256で検証します**。固定されていない/プレースホルダーのshaは現在受け入れられています（上記のゴール1ベンダー提供ギャップ。レシピデータベースとその成果物URLを信頼できるものとして扱い、それが実装されるまで）。
- **アーカイブをインスタンスごとのディレクトリに抽出します（グローバルPATHには決して追加しません）**。
- **ローカルサーバー (`127.0.0.1`) を起動し、停止できます**。ティアダウンはID検証されます（これは、インスタンスディレクトリにある実行ファイルを殺すため、関係のないプロセスを誤って終了させることはありません）。

不可逆な処理の各ステップは、実行する前に記録され、名前が付けられた最新の補正モジュールが用意されています。脆弱性を報告するには、[`SECURITY.md`](SECURITY.md) を参照してください。

## サポート

engine-room は**積極的にメンテナンス**されています。セキュリティ修正は、**最新のマイナーバージョン**（1.0.x 系）に適用されます。サポート対象のバージョンと、プライベートな脆弱性報告方法については、[`SECURITY.md`](SECURITY.md) を参照してください。バグや機能リクエストは、GitHub の Issue として提出してください。
